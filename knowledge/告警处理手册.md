# ServiceDown 服务下线
告警名称（Prometheus alertname）：ServiceDown
告警解释：服务下线通常因为服务进程 panic 崩溃导致 pod 反复重启，健康检查连续失败而触发。常见诱因：代码空指针 / 数组越界等 bug、依赖初始化失败、内存泄漏导致 OOM 被 kill。
排查步骤：
1. 先调用 get_current_time 获取当前时间，再据此搜索最近 1 小时日志。
2. 用日志工具按关键字 "panic" 搜索该服务最近 1 小时的日志。
3. 在 panic 堆栈中定位崩溃的代码文件、行号与触发函数。
4. 结合错误码（详见《服务错误类型》）判断是否为下游调用失败或数据库错误引发（错误码 12003 / 12002）。
5. 若同时出现 HighMemoryUsage 告警，用关键字 "oom"、"OOMKilled" 搜索日志，确认是否被内核杀死。
处置建议：先回滚最近一次发布恢复服务；若为 OOM，临时扩容内存并限流，再修复内存泄漏根因。

# APIHighErrorRate 接口失败率过高
告警名称（Prometheus alertname）：APIHighErrorRate
告警解释：接口失败率过高通常由服务自身异常或下游服务不可用导致。本告警的 labels.endpoint 字段给出具体接口名。
排查步骤：
1. 先调用 get_current_time 获取当前时间。
2. 用日志工具按接口名（如 /api/order/create）和关键字 "response" 搜索最近 1 小时日志。
3. 分析查询到的日志中的 error 与错误码：错误码 12003 表示下游接口错误，12002 表示数据库更新失败，12001 表示参数错误（见《服务错误类型》）。
4. 若为 12003，进一步用关键字 "downstream"、"connection refused" 搜索下游服务日志，确认下游是否不可用。
5. 若为 12002，排查数据库连接与慢查询。
处置建议：下游不可用时对下游做熔断降级；数据库问题时修复连接池 / 慢 SQL。

# ReconciliationDiff 与下游对账发现差异
告警名称（Prometheus alertname）：ReconciliationDiff
告警解释：与下游对账发现差异通常由数据同步异常或计算错误导致——上游订单成功但未同步到下游对账系统，或下游回执丢失。
排查步骤：
1. 先调用 get_current_time 获取当前时间。
2. 用日志工具按关键字 "error" 和 "reconciliation" 搜索最近 1 小时日志。
3. 根据日志中的 diff 笔数与失败的订单号，分析差异原因（同步失败 / 计算错误）。
4. 若同步失败日志中出现错误码 12002（数据库更新失败）或 12003（下游接口错误），按对应错误码处置（见《服务错误类型》）。
5. 检查是否存在上游已成功但下游未落库的"孤儿订单"。
处置建议：修复同步链路后，对差异笔数执行补偿重放；必要时人工对账。

# HighMemoryUsage 内存使用率过高
告警名称（Prometheus alertname）：HighMemoryUsage
告警解释：内存使用率过高可能由内存泄漏、大对象未释放或缓存无限增长导致，严重时会触发 OOM 导致服务被 kill 重启（常与 ServiceDown 同时出现）。
排查步骤：
1. 先调用 get_current_time 获取当前时间。
2. 用日志工具按关键字 "memory"、"oom"、"OOMKilled" 搜索最近 1 小时日志。
3. 确认是否发生 OOMKilled；若有，结合 ServiceDown 的 panic 日志判断重启是否由 OOM 引起。
4. 排查是否存在内存泄漏（GC 频繁、heap 持续上涨）。
处置建议：临时扩容内存并重启释放内存；定位泄漏点修复代码；对缓存加上限与淘汰策略。

# HighCPUUsage CPU 使用率过高
告警名称（Prometheus alertname）：HighCPUUsage
告警解释：CPU 使用率过高可能由死循环、GC 压力过大、或服务频繁重启（重启风暴）导致。若与 ServiceDown 同时出现，多半是 panic 重启循环带来的 CPU 飙升。
排查步骤：
1. 先调用 get_current_time 获取当前时间。
2. 用日志工具按关键字 "cpu"、"throttle" 搜索最近 1 小时日志。
3. 若伴随 ServiceDown，优先按 "panic" 排查服务下线根因，CPU 飙升多为重启风暴的次生现象。
4. 若无 ServiceDown，排查是否存在死循环或高耗 CPU 的计算逻辑。
处置建议：消除重启风暴根因后 CPU 通常回落；必要时临时扩容 CPU 并限流。

# DiskSpaceRunningLow 磁盘空间不足
告警名称（Prometheus alertname）：DiskSpaceRunningLow
告警解释：磁盘空间不足常由日志暴涨、核心转储（core dump）堆积或临时文件未清理导致。若与 ServiceDown 同时出现，往往是 panic 堆栈日志刷爆磁盘。
排查步骤：
1. 先调用 get_current_time 获取当前时间。
2. 用日志工具按关键字 "disk"、"no space left" 搜索最近 1 小时日志。
3. 确认告警的 labels.mountpoint 指向哪个分区（如 /data），检查该分区是否被日志文件占满。
4. 若日志暴涨由 panic 引起，结合 ServiceDown 的 "panic" 日志定位崩溃根因。
处置建议：先清理 / 轮转日志释放空间恢复服务写盘；配置日志轮转与保留策略；修复导致日志暴涨的根因。
