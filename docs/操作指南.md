# watchTower 操作指南

本篇讲**怎么把 Agent 排查闭环跑起来**，每步给出「执行命令 + 预期输出 + 数据从哪来 + 配置项」。与 [CLS与Prometheus接入配置指南.md](CLS与Prometheus接入配置指南.md) 互补：那篇重"配置接入"，本篇重"运行验证"。

> 两条路线：
> - **路线 A（本地 mock 闭环）**——无需任何云账号，用项目自带的 mock 告警 + 本地 Milvus 知识库验证「告警→文档」链路。
> - **路线 B（真实 CLS + Prometheus）**——把日志接腾讯云 CLS、告警接真实 Prometheus，跑通完整「告警→文档→日志」链路。

---

## 0. 前置：三条数据链路速查

| Agent 工具 | 代码 | 配置项 | 数据来源 |
|---|---|---|---|
| `query_prometheus_alerts` | [ai/tools/query_metric_alerts.go](../ai/tools/query_metric_alerts.go) | `prometheus.base_url` | Prometheus HTTP `GET /api/v1/alerts` |
| `query_log` | [ai/tools/query_log.go](../ai/tools/query_log.go) | `cls.*`（直连，推荐）或 `mcp_url`（MCP 回退） | 腾讯云 CLS（直连走 SearchLog API；回退走 MCP/SSE） |
| `query_internal_docs` | [ai/tools/query_internal_docs.go](../ai/tools/query_internal_docs.go) | `milvus.*` | Milvus 知识库（已索引 `docs/*.md`） |

> **`query_log` 优先级**：配了 `cls.*` → 直接调 CLS SearchLog API（稳定，不依赖 MCP token）；否则回退 MCP（需有效 `mcp_url` token）；两路都不可用 → executor 降级跳过日志工具（不阻塞告警+文档链路）。
>
> 闭环成立的三条铁律：① Prometheus 的 `alertname` == 知识库《告警处理手册》小节英文告警名；② 手册规定的搜索关键字必须真出现在 CLS 日志里；③ CLS 必须开全文索引。

- **配置项**：`etc/conf.yml` → `milvus.address: localhost:19530`、`db_name: agent`、`collection_name: biz`。

> 这 6 个 `alertname` 必须与《告警处理手册》小节英文标题一致，Agent 才能凭告警名查到处理步骤。

## 路线 B：真实 CLS + Prometheus（完整链路）

### B1. CLS 建主题 + 开索引（控制台操作）

1. 腾讯云控制台 → 日志服务 CLS → 新建日志集 + 日志主题，记下：
   - **Topic ID**（形如 `5590476b-817b-451d-91a7-655570dbd1f6`）
   - **地域**（如 `ap-chongqing`）+ **外网接入域名**（如 `ap-chongqing.cls.tencentcs.com`，本地用外网；`tencentyun.com` 是 VPC 内网，本地不可用）
2. 进主题 → **索引配置** → **开启全文索引**（关键字检索的前提，不开 `query_log` 搜不到）。
3. 在访问管理 CAM 拿一对 **SecretId / SecretKey**（上传日志 + SearchLog 鉴权用）。

**配置项**——改 [etc/conf.yml](../etc/conf.yml)（推荐：CLS 直连，无需 MCP token）：
```yaml
cls:
  secret_id: "AKIDxxxx"
  secret_key: "xxxx"
  topic_id: "你的TopicID"
  endpoint: "cls.tencentcloudapi.com"   # SearchLog API 域名（固定，非地域接入域名）
  region: "ap-chongqing"                # 与建主题时的地域一致
```

> 备选：若你有有效的 CLS MCP token，可改配 `mcp_url: "https://mcp-api.tencent-cloud.com/sse/<token>"`，`query_log` 会回退走 MCP。但 MCP token 易失效且获取入口不稳定，**推荐用上面的 `cls` 直连**。

- **数据来源**：腾讯云控制台 + CAM。

### B2. 上传日志到 CLS（官方 SDK，已验证）

```bash
export CLS_SECRET_ID="AKIDxxxx"
export CLS_SECRET_KEY="xxxx"
export CLS_TOPIC_ID="你的TopicID"
export CLS_ENDPOINT="ap-chongqing.cls.tencentcs.com"   # 地域外网接入域名
export CLS_LOG_DIR="/Users/你/watchTower/mock_data/logs"
go run ./scripts_cls/upload_cls_logs.go
```

**预期输出（已实跑验证）：**
```
[OK] mock_data/logs/node-resource.log (15 条)
[OK] mock_data/logs/order-create-response.log (11 条)
[OK] mock_data/logs/order-service-panic.log (14 条)
[OK] mock_data/logs/reconciliation-error.log (11 条)
上传完成: 成功 4 个文件, 失败 0。等待刷盘...
完成。可在 CLS 控制台检索，或让 Agent 通过 query_log 按关键字查询。
```

- **数据来源**：[mock_data/logs/*.log](../mock_data/logs/)（脚本用腾讯云官方 SDK `tencentcloud-cls-sdk-go` 逐行写入，时间散布在过去 1 小时，确保"最近1小时"检索命中）。
- **上传用 SDK 而非手撸签名**：之前手写 TC3-HMAC-SHA256 签名在 `structuredlog` 接口上反复失败（`miss param topic_id` / `Authorization Is Illegal`），改用官方 SDK 后 0 失败。生产环境也可用业务采集 agent（LogListener/Filebeat）投递。

### B3. 校验日志可检索（已实跑验证）

控制台检索框输入 `panic`，**预期**命中 20 条左右。也可用代码验证（SearchLog API，`From`/`To` 是**毫秒**级时间戳）：

实跑命中情况（参考）：
| 关键字 | 命中条数 |
|---|---|
| panic | 20 |
| error | 23 |
| reconciliation | 7 |
| memory | 9 |
| oom OOMKilled | 4 |

> 注意：`disk` 单独搜可能 0 命中——mock 日志里是 `no space left` 整串，CLS 分词后 `disk` 未必作为独立词命中。`disk write failed`/`disk space low` 这类行含 `disk` 才命中。若要改善，可调整 CLS 索引分词符或日志措辞，不影响主链路。

- **判断**：关键字能命中说明全文索引生效，Agent 的 `query_log` 才能查到。

### B4. 部署真实 Prometheus 告警规则

```bash
promtool check rules deploy/prometheus/watchtower_alerts.yml   # 语法检查
```
**预期输出：**
```
Checking deploy/prometheus/watchtower_alerts.yml
SUCCESS: 6 rules found
```

把规则文件放入 Prometheus 容器 rules 目录，`prometheus.yml` 加载后 reload（`POST /-/reload` 或 `kill -HUP`）。校验：
```bash
curl -s http://<prometheus>:9090/api/v1/alerts | jq -r '.data.alerts[].labels.alertname'
```
**预期**：出现 6 个 alertname（同 A3）。

- **数据来源**：[deploy/prometheus/watchtower_alerts.yml](../deploy/prometheus/watchtower_alerts.yml)，6 条规则 alert 名与手册一致。
- **配置项**：`prometheus.base_url: http://<你的Prometheus>:9090`。Docker 部署改 [docker/conf-docker.yml](../docker/conf-docker.yml)，K8s 改 [k8s/deploy/02-namespace-configmap.yml](../k8s/deploy/02-namespace-configmap.yml)。

### B5. 重建知识库 + 触发 Agent

同 A5（`cd ai/cmd/knowledge_cmd && go run main.go`）+ A6/A7。**区别**：此时 `query_log` 直连 CLS 能返回命中，完整跑通「告警→文档→日志→根因→报告」。

实跑验证（Agent 真实调用 `query_log` 从 CLS 查日志，日志行示例）：
```
[query_log] query="panic" total=20
[query_log] query="error" total=23
[query_log] query="reconciliation" total=7
[query_log] query="memory" total=9
[query_log] query="oom OOMKilled" total=4
```
Agent 会按手册逐个告警查对应关键字，遇到默认 1 小时窗口查 0 条时会自行扩大时间范围重查（智能行为）。

> 提示：`disk`/`no space` 关键字可能因 CLS 分词命中 0，Agent 会反复尝试不同词导致迭代偏多（接近 MaxIterations=20）。这是 CLS 索引分词 + 关键词配合问题，非代码 bug，见 B3 备注。

| 4 | CLS 直连可连 | `go test ./ai/tools/ -run TestGetLogMcpTool -v` | 工具数=1，无 err（走 cls 直连） |

### 失败定位

| 现象 | 原因 | 修法 |
|---|---|---|
| Agent 整体 panic `unexpected status code: 500` | 旧版 CLS MCP token 失效，executor 初始化失败 | 已修复：executor 降级跳过日志工具；或配 `cls.*` 直连 |
| Agent 偶发 panic 500 后中断 | deepseek 服务端瞬时 500，无重试 | 已修复：model.go 注入 5xx/429 重试 |
| `query_internal_docs` 返回旧手册内容 | Milvus 残留旧数据（去重按 `_source` 路径，路径不同没删掉） | drop collection 重建：见下方"清空知识库" |
| Agent 查不到某告警的处理方案 | alertname 与手册标题对不上 | 对齐三方告警名（见检查 1） |
| `query_log` 搜不到日志 | CLS 未开全文索引 | 主题开启全文索引（B1） |
| `query_log` 搜不到日志 | 日志时间不在"最近1小时" | 重跑上传脚本，或 Agent 自行扩大时间范围 |
| CLS 上传 `miss param topic_id` | topic_id 没放 URL query | 已修复：官方 SDK 自动处理 |
| CLS 上传 `Authorization Is Illegal` | 手写签名与 CLS 不符 | 已修复：改用官方 SDK |
| CLS 上传失败 status=413 | 日志包过大 | 分批上传（脚本已逐文件） |
| `query_prometheus_alerts` 报错 | base_url 不通或端口未起 | 确认 mock/真实 Prometheus 在跑，conf 的 base_url 正确 |
| Milvus 连接失败 | 容器未起或地址错 | `docker ps` 确认 healthy，conf 的 `milvus.address` 正确 |

**清空知识库（解决残留旧数据）**：
```bash
# 临时跑一段：drop collection 后重跑 knowledge_cmd
cat > /tmp/drop.go <<'EOF'
package main
import("context";"fmt";"watchTower/common/config";"watchTower/common/milvus")
func main(){config.InitConfig();c,_:=milvus.NewMilvusClient(context.Background())
c.DropCollection(context.Background(),config.Conf.Milvus.CollectionName);fmt.Println("dropped")}
EOF
go run /tmp/drop.go && rm /tmp/drop.go
cd ai/cmd/knowledge_cmd && go run main.go
```

## 附：6 条告警为什么是同一个根因

```
05:55 发布 order-service v1.8.2 引入 nil pointer bug (order/service.go:128)
        │
        ├─► panic 反复重启 ───────────────────► ServiceDown        (搜 "panic")
        │     ├─► 内存泄漏 OOMKilled ─────────► HighMemoryUsage    (搜 "memory"/"oom")
        │     ├─► 重启风暴 + GC ──────────────► HighCPUUsage       (搜 "cpu"/"throttle")
        │     └─► panic 堆栈日志刷爆 /data ───► DiskSpaceRunningLow(搜 "disk"/"no space left")
        │
        ├─► 重启间隙调用下游失败 code=12003 ─► APIHighErrorRate    (搜 "response" + 接口名)
        │
        └─► 失败订单未同步下游 ──────────────► ReconciliationDiff  (搜 "error"+"reconciliation", code=52002)
```

Agent 最终应能识别这是**一次发布引起的雪崩**而非 6 个独立问题，并给出"回滚 v1.8.1 + 恢复下游 + 对 23 笔差异订单补偿重放"的处置策略，对照 [mock_data/error_reports/incident-20260620-order-service.md](../mock_data/error_reports/incident-20260620-order-service.md)。
